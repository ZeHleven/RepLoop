# Food-name normalization follow-up for 0.5.46

An Agent meal request using the catalog's exact name `白米饭（中粒米，熟）`
was rejected as an unknown food. The request was normalized with Unicode NFKC,
while stored canonical names were only trimmed and lowercased. Parentheses,
commas and whitespace could therefore prevent a match or incorrectly fall
through to a lower-priority English name or alias.

Canonical name comparisons and food-name searches now apply NFKC, lowercase
and whitespace normalization to stored names as well. The catalog's original
display names and nutrition values remain unchanged. Explicit food IDs still
take precedence, inactive foods are excluded, and normalization collisions
return multiple candidates for clarification. This requires no schema migration.

Local validation used a new isolated PostgreSQL 16.15 / UTF8 database:

- Before: 14 failing and 7 passing focused regression cases.
- After: the same 21 cases pass, including canonical-name priority, ambiguity,
  inactive/unknown foods, owner-scoped private food search, and proposal lifecycle.
- Meal lifecycle: 160g proposal, revision to 200g, old proposal stale, no write
  before confirmation, and one persisted meal after duplicate confirmation.
- Full backend suite: 1791 passed, with 807 existing deprecation warnings.

The local lifecycle checks use the real proposal service and PostgreSQL; they
do not call a model or simulate a phone UI. CI, live-model release evaluation,
deployment and final phone acceptance are recorded separately for the resulting
candidate commit. The previous deployed candidate remains unchanged by this
source patch.

PostgreSQL's built-in UTF8 normalization is documented in
[String Functions](https://www.postgresql.org/docs/16/functions-string.html).
