# 开发笔记：查询修好了一层，还要走完下一层

本地草稿，未发布。配图使用合成任务和真实模型结果，非小程序现场截图。

上一轮测量中，循练有一道很普通的查询没完成：用户想看已完成训练的日期和每场时长。数据库里有30分钟和12分钟，回答却只列组数、次数和容量。接着问“改成最近3天”，又被提示暂时无法处理。

原始模型响应让排查少走了弯路。模型已经把追问识别为只读查询，误拦来自后端规则；时长字段也已经在工具结果里，漏在报告渲染。这轮先修这两处，并保留修改前代码、原始响应和工具轨迹。

新增35项回归在旧代码上有15项失败。修复后，相关测试通过，完整后端2016项也通过了。但真实模型第一候选只从14/16提高到15/16。

剩下的失败很具体：模型把“只看已完成”展开成“不纳入进行中、跳过和提前结束记录”，后面的状态解析器却不认识“纳入”。第一道校验放行了，第二道又要求用户补充已经说过的信息。

因此我补了明确排除状态的语义和16项回归，也检查双重否定、互相冲突的状态条件仍需澄清。第二个候选完整后端2032项通过，原16个任务全部完成。历史查询终于交付每场时长，改成最近3天后也能继续读取正确范围。

扩展检查仍有失败。三种新表达里，2个任务完整完成；“过去一周完成过的训练”在首次查询时被另一条既有规则误判为写入。把相同模型输出回放到未修改主线，也会失败。这条被保留为下一轮问题，没有删除、改写题目或重跑换分。

本轮三批真实调用共150次，按应用保守费率估算约0.97元，包含首候选未完成任务和所有重试。它不是实际账单。数据库确认前后的状态也逐项检查，旧提案重新确认被拒绝。

本轮原问题已修好，但这不等于查询能力已经覆盖所有说法。原16题是固定开发回归，扩展题也由同一实施者编写和复核。手机等待、真人纠正次数和满意度，仍需上线后真实采集。
